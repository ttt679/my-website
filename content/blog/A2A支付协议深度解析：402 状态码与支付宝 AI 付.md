## 引言

想象这样一个场景——

你用 AI 助手整理一份合同，助手发现有几段需要专业翻译，于是它自动调用了一个翻译 API。

不到两秒，结果回来了。

账单上多了一笔 0.05 元的扣款。没有跳转支付页面，没有扫码，没有你按"确认付款"。

一切都在两个 AI 之间悄悄完成了。

这不是科幻。让它成为现实的，是一个被遗忘了整整 30 年的 HTTP 状态码——

**402 Payment Required。**

## 一、收钱，是 AI 时代最难解的工程问题之一

过去两年，AI 智能体的数量呈指数级增长。

从简单的问答机器人，到能自主规划、调用工具、协同完成复杂任务的 Agent，整个生态正在从"单打独斗"走向 **A2A 协作**——一个智能体调用另一个智能体的服务，形成真正的 AI 供应链。

这带来了一个绕不过去的问题：**谁来付钱？怎么付？**

传统的互联网支付流程是为人设计的：看到价格→点击购买→跳转扫码→输入密码。核心假设是**人在中间**，有人看、有人决策、有人操作。

但 AI 智能体不是人。

它没有手，无法扫码，不会点"确认付款"。每次调用付费服务都要中断流程等人来操作，"自主智能体"就变成了一个需要人全程盯着的助手，毫无意义。

传统解法是 OAuth 授权 + 预存信用卡，但链路复杂，每个平台都要单独接入，对独立开发者几乎是噩梦。

**能不能有一种原生于 HTTP 协议的方式，让 AI 之间的支付像普通接口调用一样自然？**

这个问题，一个 30 年前的状态码给出了答案。

---

## 二、402：沉睡三十年，终于等来它的时代

1991 年，HTTP 协议的设计者在草案里预留了 `402 Payment Required` 这个状态码。

当时的想法很朴素：未来互联网可能会有"微支付"需求，服务器可以用 402 告诉客户端"你得先付钱"。

然而这个设想超前了时代太多。没有生态，没有标准，没有落地场景，402 就这样在规范里挂着，沉睡了整整三十年，几乎被所有人遗忘。

直到 AI 智能体时代到来。

---

### A2A 支付的完整闭环，只有三步

**第一步：请求 → 收到 402**

用户智能体向商户智能体发起请求（比如"帮我翻译这段话"）。商户智能体发现请求中没有支付凭证，返回 `402 Payment Required`，响应体里包含：

```json
{
  "payment_url": "https://qr.alipay.com/xxx",
  "order_id": "2026060812345678",
  "amount": "0.05",
  "currency": "CNY",
  "expires_at": "2026-06-08T15:10:00Z"
}
```

支付链接、订单号、金额、过期时间——清晰，标准，机器可读。

**第二步：完成支付 → 获得凭证**

用户智能体通过支付宝 AI 付完成支付，拿到一个 `payment_proof`（支付凭证）——这是由支付宝服务端签名的加密数据，证明"这笔钱已经付了"。

**第三步：带凭证重试 → 获得服务**

用户智能体将 `payment_proof` 附在原始请求里重新发送。商户智能体验证凭证，通过后执行业务，返回翻译结果。

整个过程，用户（人类）可以完全不介入。

---

### payment_proof：整个协议安全性的核心

`payment_proof` 不是随机字符串，它是由支付宝服务端签名的结构化数据，包含：

- 订单 ID，防止凭证被复用到其他订单
- 支付时间戳，防止重放攻击
- 商户 App ID，确认收款方身份
- 支付宝的 RSA 签名

最关键的设计原则：**商户必须将这段数据发给支付宝服务端校验，不允许本地自行验证。**

伪造的凭证无法通过验证，过期的凭证无法重复使用，一个凭证无法跨订单使用——安全性由协议本身保证，而不是依赖商户自己写得对不对。

## 三、支付宝 AI 付：把协议变成可以用的产品

如果说 402 协议是一张设计图，支付宝 AI 付就是把它建出来的施工队。

### AI 付 vs AI 收：两个角色，一套生态

支付宝将这套能力拆成了两个方向：

**AI 付**，面向用户侧智能体。让 AI 助手内置自动付款能力，用户授权一次，助手此后可以在额度范围内自主完成支付，无需每次人工确认。

**AI 收**，面向商户侧。商户在支付宝开放平台创建"AI 商品"，设定单价，系统自动生成符合 ACT 协议的收款接口——从此这个服务对所有 AI 智能体都是"可付费可调用"的。

两者通过 **MCP Server**（Model Context Protocol 服务）连接。支付宝官方提供了现成的 MCP 工具，95% 的主流智能体框架都可以直接接入，不需要自己写对接代码。

### 商户入驻，只需要三步

要让自己的服务具备 A2A 收款能力：

1. 在支付宝商家平台完成实名认证
2. 在支付宝开放平台创建"AI 智能体支付服务"应用，填写服务名称和单次定价
3. 获取 App ID、支付宝公钥、商户私钥

完成之后，你的 AI 服务就正式"上架"到了 AI 经济的货架上。

但这里有一个很多人没意识到的陷阱。

---

## 四、最后一公里：入驻了，但智能体还不会"收钱"

很多开发者完成入驻之后，以为大功告成。

结果当用户智能体真的发来一个带 `payment_proof` 的请求时，自己的智能体完全懵了——

它不知道如何生成 402 响应体。

它不知道如何调用支付宝接口验证凭证。

它也不知道如何防止同一个凭证被重复提交。

这就是 A2A 支付在商户侧的**最后一公里问题**：协议有了，基础设施有了，但"让智能体真正学会收钱"那段代码，没人帮你写好。

---

## 五、AgentPay Gateway：把收钱这件事变成几行代码

面对这个问题，一种典型的解法是引入**支付网关层**，把 402 生成、凭证验证、防重放等逻辑从商户智能体里抽离出来，做成独立的云函数服务。

架构看起来是这样的：

```
用户智能体
    ↕  HTTP 请求
商户智能体（只写业务代码）
    ↕  转发请求
支付网关云函数
    ↕  调用官方接口
支付宝 AI 收 SDK
```

商户智能体只做一件事：把用户的请求转发给网关，根据网关返回的结果决定下一步。支付相关的所有复杂逻辑，全部由网关代劳。

### 两次请求的核心差异

**无凭证的第一次请求**：网关检测到没有 `payment_proof`，生成订单，返回 402 响应体，商户原样转发给用户。

**带凭证的第二次请求**：网关提取 `payment_proof`，调用支付宝服务端验证，成功后返回：

```json
{
  "verified": true,
  "request": { "text": "Hello" }
}
```

注意：**网关不执行任何业务逻辑**，只做支付验证，把去掉凭证的原始参数原路返回。商户自己调用翻译函数、处理结果、回复用户。

这样商户智能体的上下文保持干净，不会被支付逻辑污染。

### Python 接入示例

```python
import requests

GATEWAY_URL = "https://your-gateway.com/v1/payment"
API_KEY = "sk_live_abc123"

def handle_user_request(request_body):
    resp = requests.post(
        GATEWAY_URL,
        headers={"X-API-Key": API_KEY},
        json=request_body
    )
    if resp.status_code == 402:
        return resp.json(), 402           # 转发 402 给用户智能体
    elif resp.status_code == 200:
        data = resp.json()
        if data.get("verified"):
            result = do_my_business(data["request"])  # 执行业务
            return {"result": result}, 200
    return {"error": "gateway error"}, 500
```

核心逻辑只有这几行：转发 → 判断状态 → verified 为 true 就执行业务。

## 六、A2A 支付的生态意义

这件事的影响，比大多数人想象的要深远。

### 它让 AI 服务真正"商品化"

在 A2A 支付出现之前，AI 服务之间的调用是免费的，或者靠 API Key 订阅制管理——本质上还是人与人之间的商业协议，AI 只是执行者。

有了 A2A 支付，AI 服务可以以极细的粒度定价：一次翻译 0.05 元，一次图片处理 0.2 元，一次法律文本审核 2 元。这些微交易的对手方是 AI，发生在毫秒级，不需要人工审批，也不需要预先签合同。

这是互联网历史上第一次，**机器可以在没有人类中间人的情况下完成商业交易**。

### 它打开了一个新的开发者市场

任何有一技之长的开发者——会写翻译模型的、会处理合同的、会分析数据的——都可以把自己的能力封装成一个 AI 服务，挂上支付宝 AI 收，等待其他 AI 来调用。

这是一种全新的"睡后收入"：你写好代码，24 小时被 AI 调用，钱自动进账，你甚至不知道它今天被调用了多少次。

### 它让生态真正跑起来

一个 AI 经济生态能否真正繁荣，关键在于有没有足够多的"可付费服务"供 AI 选择。

A2A 支付协议的普及，会快速积累起一个庞大的付费 AI 服务目录。随着这个目录变得更丰富，用户智能体的能力边界会大幅扩展——它们可以随时按需"购买"自己缺少的能力，而不是只能依赖预先集成的工具。

这是一个正向飞轮，而它的核心，是一个 30 年前没人用过的 HTTP 状态码。

## 结语

回到开头那个场景：AI 助手帮你翻译合同，账单上多了 0.05 元。

这件事背后的链条是：

- 1991 年，HTTP 草案预留了 `402`，但没人知道该怎么用
- 2024 年，AI 智能体爆发，A2A 协作成为趋势
- 支付宝发布 ACT 协议，把 402 变成了标准收款暗语
- AI 付 / AI 收把协议变成了可以入驻的产品
- 支付网关这样的工具把"会用协议"变成了"几行代码"

**402 不只是一个支付状态码，它是 AI 自主经济的起点。**

它的意义在于：从此，AI 之间的价值交换，不再需要人类作为中间人按下确认键。

我们正站在一个节点上——基础设施已经齐备，但大多数人还没意识到这意味着什么。
